1. WAS IST DAS HIER ÜBERHAUPT?

Willkommen beim Stock Data Node! Dieses Programm ist dein persönlicher Sklave, wenn es darum geht, historische Kursdaten direkt von Interactive Brokers (IBKR) zu rauben. Es ist kein einfaches "Download-Skript", sondern ein hochintelligenter Knotenpunkt, der genau weiß, wann welche Aktie an welcher Börse gehandelt wird und welche Daten dir noch in deiner Sammlung fehlen.

Das Ziel: Eine lückenlose Datenbank im Parquet-Format, die du für Backtests, Analysen oder zum Angeben nutzen kannst.

2. DIE MAGIE UNTER DER HAUBE (LOGIK)

Das Programm arbeitet mit mehreren "Gehirnzellen", die ständig im Hintergrund laufen:

  • Der Watcher: Er starrt ununterbrochen auf den Ordner watch/. Sobald du dort eine Datei mit Tickern reinwirfst, wacht er auf.
  • Die API: Ein kleiner Webserver, der auf Befehle von außen wartet (z.B. von anderen Programmen oder Tools).
  • Die Priority-Queue: Hier wird entschieden, wer zuerst dran ist. API-Anfragen haben immer Vorrang vor automatischen Hintergrund-Updates.
  • Chunking & Delta: Wenn du 20 Jahre Historie willst, lädt das Programm nicht alles in einem Riesen-Kasten. Es zerlegt die Zeit in kleine "Chunks". Dabei merkt es, wenn du schon Daten hast (Delta-Erkennung) und lädt nur das, was fehlt.
  • Preemption (Vordrängeln): Wenn gerade ein riesiger Hintergrund-Job läuft und du plötzlich über die API einen Ticker anfragst, unterbricht das Programm den Job kurzzeitig, erledigt deine Anfrage und macht danach brav weiter.
  • Auto-Discovery: Kennst du die genauen Börsendaten für eine Aktie nicht? Kein Problem. Das Programm sucht bei IBKR nach dem Symbol und wählt basierend auf Prioritäten (Währung, Börse) das beste Ergebnis aus.

3. BEDIENUNGSANLEITUNG (WATCH-FILES)

Der einfachste Weg, den Node zu füttern, ist das Hinterlegen von Dateien im watch/ Ordner.

Zulässige Formate

  • Dateiendung: Muss zwingend .txt sein.
  • Inhalt: Ticker-Symbole (Groß-/Kleinschreibung egal), die durch **Leerzeichen**, **Kommata** oder **Zeilenumbrüche** getrennt sind.

Beispiel für eine gültige Datei:

    AAPL, MSFT
    TSLA NVDA AMD
    Intel, IBM

Lebenszyklus einer Watch-Datei

  1. Du kopierst die Datei in den Ordner watch/.
  2. Der Node erkennt die Datei (innerhalb von max. 10 Sek.).
  3. Eine Kopie wird zur Sicherheit in data/watchlists/ abgelegt.
  4. Die Ticker werden extrahiert und mit Hintergrund-Priorität in die Warteschlange eingereiht.
  5. Erfolg: Wenn alle Ticker erkannt wurden, wird die Datei im watch/ Ordner gelöscht.
  6. Teilerfolg/Fehler: Wenn Ticker nicht aufgelöst werden konnten (und Auto-Discovery scheitert), wird die Datei überschrieben und enthält danach nur noch die problematischen Ticker zur manuellen Prüfung.

4. DIE REST-API REFERENZ

Für die Integration in eigene Scripte bietet der Node eine REST-API (Standardmäßig auf Port 8002).

Methode Endpunkt Beschreibung
POST /download Fügt einen Ticker mit höchster Priorität hinzu.
POST /trigger-staleness Prüft alle vorhandenen Daten auf Aktualität und lädt Fehlendes nach.
GET /status Gibt die aktuelle Größe der Warteschlange zurück.
GET /health Einfacher Liveness-Check (für Docker/Monitoring).

Beispiel: Download anfordern

Sende einen POST-Request an http://localhost:8002/download mit folgendem JSON-Body:

{
  "ticker": "AAPL",
  "timeframes": ["1D", "1h"]
}

Hinweis: Wird timeframes weggelassen, verwendet der Node die Standard-Einstellungen aus der Konfiguration.

5. LOGS LESEN FÜR FORTGESCHRITTENE

Das Terminal-Log nutzt ANSI-Farben zur schnellen Orientierung:

  • CYAN: Ticker-Symbole. Erreicht das System einen Meilenstein für einen Ticker, leuchtet er hier auf.
  • MAGENTA: Metriken. Anzahl der geladenen Kerzen, Dauer des Requests oder Anzahl der Chunks.
  • GELB (WARN): Pacing-Verstöße oder kurzzeitige Verbindungsprobleme. Das System regelt hier automatisch ab (Exponential Backoff).
  • ROT (ERROR): Kritische Abbruchbedingungen (z.B. "Invalid Contract").

Pro-Tipp: Achte auf die "════" Trennlinien. Sie markieren den Start einer neuen Phase (z.B. Initialisierung oder Abschluss eines kompletten Download-Zyklus).

6. DIE JSON-GEHEIMNISSE

Hier wird das Gehirn konfiguriert:

  • config/ticker_map.json: Die wichtigste Datei. Sie mappt Ticker auf IBKR-Verträge.
    Format: "AAPL": {"symbol": "AAPL", "exchange": "SMART", "currency": "USD"}
  • state/failed_ticker.json: Die Blacklist. Hier landen Ticker, die auch nach mehreren Versuchen nicht geladen werden konnten (Grund wird mitgespeichert).
  • config/auto_discovery.json: Hier definierst du, welche Börsen (z.B. SMART, XETRA) und Währungen bei der automatischen Suche bevorzugt werden sollen.

7. DIE PARQUET-SCHATZKAMMER

Deine Daten landen im Ordner data/parquet/. Struktur: [TICKER]/[TIMEFRAME].parquet

Vorteile von Parquet:

  • Kompression: Bis zu 90% kleiner als CSV.
  • Typensicherheit: Zeitstempel und Kurswerte sind exakt definiert.
  • Speed: Perfekt für Python Bibliotheken wie pandas oder polars.

8. DER STALENESS-CHECKER (STANDALONE SCRIPT)

Wenn du nur mal eben prüfen möchtest, wie aktuell deine Daten wirklich sind, ohne direkt einen Download-Zyklus zu starten, gibt es dafür ein eigenes Tool.

Starten des Scripts: 

    ./check_staleness.sh

Dieses Script liest direkt aus deiner Parquet-Datenbank den neuesten Timestamp für jeden Ticker aus und berechnet die Verteilung des "Alters" (in Tagen). Das Resultat ist eine kompakte Übersicht in der Konsole, sortiert nach dem prozentualen Anteil (höchster Anteil zuerst).

Tipp zur Priorisierung: Der Node selbst nutzt diese Logik ebenfalls! Bevor automatische Hintergrund-Updates (Staleness Sweeps) gestartet werden, rechnet das System aus, welche Ticker am längsten nicht mehr aktualisiert wurden (oder noch gar nicht existieren). Diese "outdated" Ticker rutschen in der Download-Queue ganz nach vorne!
